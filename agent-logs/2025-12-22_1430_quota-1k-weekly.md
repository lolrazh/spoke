# Free Tier Quota: Monthly to Weekly Migration (2000 → 1000 words)

**Date:** 2025-12-22
**Agent:** Claude Sonnet 4.5
**Status:** ✅ Completed

## User Intention

The user wanted to change the free tier quota from a monthly cadence (2000 words/month) to a weekly cadence (1000 words/week), resetting every Monday at 00:00 UTC. The motivation was to provide a more generous psychological experience—users get a fresh start every week instead of waiting up to a month for quota reset, and if they hit their limit mid-week, they only wait a few days instead of potentially weeks.

Additionally, the user wanted to rename the database column and JWT claim from `words_used_this_month` to `words_used_this_week` to better reflect the weekly cadence.

## Key Learnings

- **PostgreSQL date_trunc('week')** - Uses Monday as week start by default, which is exactly what the user wanted (no configuration needed)

- **Lazy reset pattern is cadence-agnostic** - The existing "lazy reset on JWT refresh" architecture supports weekly resets without any structural changes—only the date calculation changes from `date_trunc('month', ...)` to `date_trunc('week', ...)`

- **JWT claim renaming requires coordinated deployment** - Changing the JWT claim name (`words_used_this_month` → `words_used_this_week`) means:
  - Old apps will read undefined from new JWTs → local quota shows 0
  - Server-side enforcement still works correctly (worker updated)
  - Users should update app to see correct quota in UI

- **Weekly quota psychology** - 1k/week (52k/year potential) vs 4k/month (48k/year potential) has similar annual limits, but weekly feels more generous because:
  - Shorter feedback loop (week vs month)
  - "Fresh start Monday" is psychologically positive
  - If quota hit mid-week, only 3-4 day wait vs potentially 2+ weeks

## Architecture Decisions

- **Keep existing quota system architecture** - Only changed limits/cadence, not the flow:
  - **Why:** Server-authoritative design is already production-grade and tamper-proof
  - **Result:** Minimal code changes (mostly find-and-replace), low risk

- **Rename JWT claim to match cadence** - Changed `words_used_this_month` → `words_used_this_week`:
  - **Why:** More accurate naming, clearer intent for future developers
  - **Trade-off:** Requires app update for users to see correct quota display
  - **Acceptable:** Server-side enforcement unaffected, users just see stale UI until update

- **1k/week instead of 4k/month** - Chose weekly cadence over increasing monthly limit:
  - **Why:** Better UX (predictable Monday resets, shorter wait if quota exceeded)
  - **Trade-off:** Less flexibility (can't "save up" for big month)
  - **User preference:** Psychological benefits outweighed flexibility

## Backward Compatibility Note

**Old app versions with new JWT:**

When old app (expects `words_used_this_month`) receives new JWT (contains `words_used_this_week`):

1. **App side (local quota check):**
   - `payload.words_used_this_month` → `undefined`
   - Defaults to `0` in conditional checks
   - **Result:** Progress bar shows "0 / 2000" (old hardcoded limit)
   - Local quota check always passes (0 < 2000)

2. **Worker side (server enforcement):**
   - Updated worker reads `jwtResult.wordsUsedThisWeek` correctly
   - Enforces actual usage against 1000 limit
   - **Result:** Server-side gating works perfectly

**Impact:** Old clients show incorrect quota in UI but are still correctly gated server-side. Users should update app to see accurate quota display.
